## 1 · 浅色模式反提

### 1.0 一句话总纲

深色模式的层级感来自**加光**：底够黑 → 加一层更亮的面 → 加一条 1px 内描边 → 加一抹顶边内高光 → 加一片环境落影。五个动作全都在「往暗处加光」。

浅色模式**不能照抄**，因为浅底已经接近亮度上限（页面底 `#EFF1F4` 的 L\* = **95.07**，纯白 L\* = 100.00，只剩 4.93 的余量）。同样的五个动作在浅底上要么看不见、要么把面糊成一片白。

> **浅色总纲：面比底更亮（不是更暗）+ 极淡边界 + 更柔的落影。**
> **禁令：不得靠加粗边框造层级；不得靠提高墨色对比硬造层级。**

两条禁令的理由不同，分开说：

- **不得靠加粗边框**：深色下描边是「在暗底上描一条亮线」，1px 已经足够，加粗会立刻变成"线框感"。浅色下描边是「在白面上描一条灰线」，加粗同样变成线框感；而且浅色描边**每加粗一倍，视觉重量增加远多于深色**（因为线与底的对比方向相反——深色线亮于底、浅色线暗于底，暗线在白底上的可见度天然更高）。所以浅色描边只能比深色**更细、更淡**，不能更粗。
- **不得靠提高墨色对比**：深色正文 `#F5F6F7` 对卡面 **16.42:1**，浅色正文 `#17181A` 对白卡 **17.77:1**——两边都已经远超 AA（4.5:1）与 AAA（7:1）。**再往上没有层级可言**（都是"极黑"），只会把页面变成黑白印刷。层级必须由**面**承担，不能由**字**承担。

### 1.1 规律一 · 材质层级（4 层）

| | 深色（v2 原值） | 浅色（v3 新值） |
|---|---|---|
| L0 页面底 | `#0B0B0C` | `#EFF1F4` |
| L1 卡片面 | `#121214` → `#17181A` | `#FFFFFF` |
| L1 凹入面（卡内分区） | `#1F2022` | `#F4F6F9` |
| L2 卡内行分隔 | `rgba(255,255,255,.045)` | `rgba(23,24,26,.045)` |
| L3 悬浮层 | `rgba(36,37,40,.62)` + `blur(22px)` | `rgba(255,255,255,.78)` + `blur(22px) saturate(1.8)` |
| 分层三件套 | 1px 内描边 `rgba(255,255,255,.06)`<br>+ 顶边内高光 `rgba(255,255,255,.05)`<br>+ 环境落影 `0 18px 40px rgba(0,0,0,.5)` | 1px 内描边 `rgba(23,24,26,.055)`<br>+ **取消**顶边内高光<br>+ 更柔落影 `0 1px 2px rgba(24,20,14,.05), 0 8px 24px rgba(24,20,14,.06)` |
| L0→L1 亮度差 | `#0B0B0C`→`#121214`：ΔL\* = **5.17** | `#EFF1F4`→`#FFFFFF`：ΔL\* = **4.93** |
| L1→凹入 | `#121214`→`#17181A`：ΔL\* = **4.00** | `#FFFFFF`→`#F4F6F9`：ΔL\* = **3.19** |

**为什么。**

1. **方向反了。** 深色里「层级往上走 = 越来越亮」，浅色里「层级往上走 = 越来越白」。页面底 `#EFF1F4` 是灰白，卡片面是纯白 `#FFFFFF`——**面比底亮**。这是浅色不同于深色的第一件事，也是整节所有推导的地基。
2. **亮度差被刻意配成镜像。** 深色 L0→L1 是 5.17，浅色取 4.93（误差 <5%）；深色 L1→凹入是 4.00，浅色取 3.19。为什么会差？因为纯白 `#FFFFFF` 是硬顶，凹入面只能往下降到 `#F4F6F9`，可用的下降空间本来就比深色小。这个 3.19 是**能达到的最大值**，不是随手取的。
3. **顶边内高光必须取消。** 它的物理含义是"光从上方来，打在上边缘"。深色下它有效，因为底色暗、一抹 `.05` 的白就看得出来。浅色下面已经是 `#FFFFFF`（255,255,255），**物理上加不了光**——任何"更亮"的内高光在数学上等于 0。硬写 `rgba(255,255,255,.05)` 只会得到一个完全不渲染的空声明。替代方案是**把内高光换成极淡的内下阴影**（可选）：浅色卡的"体积感"靠**落影**和**面本身的纯白**承担，不靠内高光。
4. **落影要更柔、更近。** 深色落影 `0 18px 40px rgba(0,0,0,.5)` 之所以敢这么大这么黑，是因为深底上黑影几乎不显脏（底的 L\* 才 3.04，黑影压上去差别不大），它只提供"浮起来"的心理暗示。浅色底 L\* = 95.07，任何黑影都会**立刻显脏**。所以浅色落影改为**双层**：一层 1px 的贴近细影（做边界）+ 一层 8px 的柔和弥散影（做浮起），alpha 从 `.5` 降到 `.05`/`.06`。
5. **L2 行分隔仍然必须比卡描边更淡**（v2 原规则保留）。深色是 `.045` 白，浅色是 `.045` 黑。数值相同、方向相反——这条规律跨模式**不变**，因为它约束的是"两级线不能打架"，与明暗无关。
6. **L3 毛玻璃在浅色下要加 `saturate`。** v2 §9 实测记录过「毛玻璃在近黑底偏灰白」；浅色底的问题是**反向的**：白毛玻璃叠在灰白底上会把背后的彩色内容洗成灰。把 `saturate` 从 1.4 提到 1.8 是补偿手段。**注意：这一条是推断，未实测（见 §6）。**

### 1.2 规律二 · 圆角（单调递增 + 同心）

| | 深色（v2 原值） | 浅色（v3 新值） |
|---|---|---|
| `--r-s` 图标底座 | `10px`（= 边长 34px 的 30%） | **不变** |
| `--r-m` 卡内元素 | `14px` | **不变** |
| `--r-l` 卡片 | `22px`（≈ 卡宽 5.6%） | **不变** |
| `--r-xl` 大分区 | `28px` | **不变** |
| `--r-full` 胶囊 | `999px` | **不变** |
| 同心关系 | 卡内圆角 ≈ 外卡 × **0.6**（22 → 14，22×0.6=13.2） | **不变，但约束收紧** |

**为什么。**

1. **圆角是几何，不是光。** 它不随明暗变化，所以数值全部沿用。**别因为"浅色看起来更轻"就把圆角改小**——那会让两套模式的几何对不上，同一个组件在两个模式下换形，是比配色不一致更严重的问题。
2. **但同心关系在浅色下更严格。** 深色的卡内分区靠「`#1F2022` 对 `#17181A`」的亮度差 + 一条 `.045` 描边双重定位，圆角哪怕差 1px 也被描边兜住。浅色卡内分区靠**纯底色差**定位（`#F4F6F9` 对 `#FFFFFF`，ΔL\* 仅 3.19），**没有描边兜底**，圆角不齐会立刻被看出来。→ 浅色下「卡内圆角 = 外卡 × 0.6」从"美学建议"升级为**硬约束**，且必须真的取整到 14px。
3. **顺带修一处 v2 与实现的不一致。** v2 §1.2 写 `--r-m: 14px`，而 `design-system/_build.mjs` 第 95 行写 `--r-m: 16px`。按第 2 条，`--r-m` **必须锁 14px**——若取 16px，则 22 → 16 的比值是 0.727，不满足 0.6 的同心关系。**v3 起以 14px 为准，实现侧需改。**

### 1.3 规律三 · 间距与尺寸节奏

| | 深色（v2 原值） | 浅色（v3 新值） |
|---|---|---|
| 间距刻度 | 只走 `4 / 8 / 12 / 16 / 20 / 24` | **不变** |
| 卡内 padding | `16–18px` | **`18–20px`（+2）** |
| 卡片之间 | `12px` | **`16px`（+4）** |
| 行高 | `52–56px`（= 34px 底座 + 上下各 ~10px） | **不变** |
| 图标底座 : 符号 | `34 : 18`（符号占 52%） | **不变** |
| 底座底色 | `#1F2022` 靠亮度差自然成立 | `#F4F6F9` + **必须补** `inset 0 0 0 1px rgba(23,24,26,.05)` |
| 大数字 : 小标签 | `44px : 10.5px` ≈ **4.2 : 1** | **不变** |
| 大数字字距 | `−0.03 ~ −0.04em` + `tabular-nums` | **不变** |

**为什么。**

1. **间距为什么要加。** 深色的阴影又大又黑，卡片自带"聚拢感"，12px 的间距已经读得出分组。浅色的阴影变柔（见 1.1 第 4 条），卡片的视觉重量整体下降，**同样的 12px 会显得比深色更挤**——因为卡片不再"占地方"了。补偿方式是把间距往上走一档：卡内 +2（16→18），卡间 +4（12→16）。两处都仍在 4 的倍数刻度上，**没有破坏 v2 的间距纪律**。
2. **底座必须补描边。** 深色的图标底座 `#1F2022` 对卡面 `#17181A`，ΔL\* = 4.00，靠亮度差自己就立得住。浅色底座 `#F4F6F9` 对白卡，ΔL\* = 3.19，**比深色还小**，单独存在时会糊掉。补一条 `inset 0 0 0 1px rgba(23,24,26,.05)` 即可——注意这是**内描边**，占的是底座自己的 1px，不改变布局尺寸。
3. **4.2:1 的字号关系跨模式不变。** 它约束的是"金额是主角、标签是配角"，与明暗无关。深色下大数字用白 `#F5F6F7`（16.42:1），浅色下用近黑 `#17181A`（17.77:1），**两边都远超 AA**，所以这个层级完全由**字号差**承担，不由颜色承担。→ 推论：**浅色下绝不允许把大数字改成品牌蓝来"提亮"**——那会把层级从"大小"偷偷换成"颜色"，破坏跨模式一致性（详见 §3 用量纪律）。

### 1.4 规律四 · 文字 4 阶（**本次必须修正的地方**）

v2 的 4 阶在深色下就**已经有两个不达标**，v3 一并修正，并给出浅色镜像。

| 阶 | 用途 | 深色 v2 | 深色 v3（修正） | 浅色 v3 | 浅色实测对比度 |
|---|---|---|---|---|---|
| T1 | 金额、标题 | `#F5F6F7` | 不变 | `#17181A` | vs 底 `#EFF1F4` **15.70:1** / vs 白卡 **17.77:1** |
| T2 | 正文、账户名 | `#A2A4AB` | 不变 | `#5C616B` | vs 底 **5.50:1** / vs 白卡 **6.22:1** |
| T3 | 辅助、单位、时间 | `#7A7C83`（**4.26:1，不达 AA**） | **`#85878E`** | `#666B75` | vs 底 **4.73:1** / vs 白卡 **5.35:1** |
| T4 | 轴刻度、页脚说明 | `#5C5E65`（**2.74:1，FAIL**） | **降级为「非文本色」** | **降级为「非文本色」** | — |

**深色 v3 实测（vs 卡面 `#17181A` / vs 页面 `#0B0B0C`）**：
`#F5F6F7` 16.42 / 18.18 · `#A2A4AB` 7.14 / 7.90 · `#85878E` **4.95 / 5.48** · `#7A7C83` 4.26 / 4.72 · `#5C5E65` 2.74 / 3.04。

**为什么。**

1. **v2 的 T3 `#7A7C83` 只有 4.26:1，T4 `#5C5E65` 只有 2.74:1，两者都低于 WCAG AA 的 4.5:1。** v2 §1.4 那句「每降一阶亮度约 −35% 且字号同步下降」在深底上是**过度衰减**：从 T2 的 7.14 直接掉到 4.26，跨过了 4.5 这条线。这是本次反提过程中被顺带查出来的**既有缺陷**（不是浅色引入的）。
2. **修正只动一个数**：T3 `#7A7C83` → `#85878E`（4.95:1）。亮度上调 ~4%，视觉上几乎无感，但把这一阶从"不达标"变成"达标且有 10% 余量"。备选 `#82848B`（4.76，余量太薄）与 `#888A91`（5.15，与 T2 的 7.14 拉得太近），**取中间值 `#85878E`**。
3. **T4 不修，直接取消。** `#5C5E65` 要升到 4.5:1 需要变成 `#82848B` 附近——那就与 T3 合并了，"4 阶"名存实亡。更诚实的做法是承认：**深色下能承载文字的安全墨色只有 3 阶**。T4 改为**非文本色**，只用于纯装饰（分隔点、网格线、禁用态填充、轴刻度的短线），**不承载任何文字**。v2 §1.4 里"「View all ›」与轴刻度是非操作文本"这条语义保留，但它们要改用 **T3**。
4. **浅色也照此办，且多一个坑。** 浅色 T3 `#81868F` 只有 **3.23:1**（不达标）、T4 `#9AA0AA` 只有 **2.32:1**（FAIL）——比深色更糟，因为浅底亮度高，灰字很容易"化"进底里。修正：浅色 T3 取 **`#666B75`**（4.73:1），T4 同样降级为非文本色。备选 `#6A6F79`（4.46，差一点点）与 `#646973`（4.87，与 T2 的 5.50 拉得太近），**取 `#666B75`**。
5. **跨模式对照表（两边都达标后）**：T1/T2/T3 的对比度深色是 16.42 / 7.14 / 4.95，浅色是 17.77 / 6.22 / 5.35。**两条曲线形状一致（高→中→低），且都不触线**，说明这套 3 阶在两个模式里是同一种"语气"。

### 1.5 规律五 · 动效 7 条

| # | v2（深色） | v3（浅色改法） | 为什么改 |
|---|---|---|---|
| 1 | 胶囊白底横向擦入 `240ms cubic-bezier(.2,.8,.2,1)` | **不变** | 白胶囊在深底是"亮块擦入"，在浅底是"白块擦入"。方向感来自**位移**不来自明暗，两端都成立 |
| 2 | 折线 `stroke-dasharray` 描线 `1.2s` | **不变** | 纯几何动效 |
| 3 | 毛玻璃 `blur 22→28`，底 `.62→.78` | `blur 22→28`，底 `rgba(255,255,255,.78)→rgba(255,255,255,.90)`，`saturate 1.8`（**未实测**） | 浅底上"更实"要靠**更白**而不是更黑 |
| 4 | 卡片按下 `scale .985` + 内高光 `.05→.10` | `scale .985` + **落影收紧**（`0 8px 24px` → `0 2px 8px`）+ 底色 `#FFFFFF → #FAFBFC` | 深色靠"加光"表达按下；浅色已经到白顶，加不了光，改靠**减光 + 影子收近**（"被按住 = 贴地了"） |
| 5 | 图标底座选中**只提亮内高光、底色不变** | **底色 `#F4F6F9 → #E9ECF1` + 描边加深到 `rgba(23,24,26,.09)`**，同样**不换色相** | 深色的纪律是"选中不改色相"；浅色无法提亮内高光（见 1.1 第 3 条），改用**下压一阶底色**达成同一个纪律 |
| 6 | 录音长按，青柠 `#C8F169` 环形声波 3 圈错开 `120ms` | 色值换成 **`--accent` 冰川蓝**（深 `#7FE3FF` / 浅 `#1B5FD0`），3 圈 / `120ms` **不变** | 青柠退场（见 §3），但"唯一强色块在录音时让位给录音态"这条**让位逻辑保留** |
| 7 | 全局 `--ease` / `--dur: 200ms`，**无 bounce** | **不变** | 纪律性约束，与明暗无关 |

**统一解释。** 7 条里有 5 条原样保留。改的 3 条（#3 #4 #5）**全部是同一个原因**：深色的动效反馈大多依赖"加光"，而浅色底已经到亮度上限，**加不了光**。凡是 v2 里"提亮内高光"的动作，浅色必须换成"下压底色"或"收紧影子"。这不是美学偏好，是**物理约束**——`rgba(255,255,255,.05)` 叠在 `#FFFFFF` 上的数学结果是**零变化**。

### 1.6 规律六 · 色彩语义与「唯一强色块」配额

语义色本身见 §3。这里只回答配额问题。

**v2 的原规则**：整页**唯一强色块** = 那张资产卡的蓝色渐变（`#7FE3FF → #3B6FE0 → #2A2F8F`），其余一切（含青柠 `#C8F169`，面积 ≤5%、支出铜橙 `#D9794F`）都是低饱和或小面积。

**浅色下这个配额是否成立？——成立，而且必须收紧。**

| | 深色 | 浅色 |
|---|---|---|
| 页面底亮度 | L\* = **3.04**（`#0B0B0C`） | L\* = **95.07**（`#EFF1F4`） |
| 底 → 卡面的亮度差 | ΔL\* = **5.17** | ΔL\* = **4.93** |
| 第二强色块会被谁吸收 | **被底吸收一部分**（暗底本身是大面积低亮度，高饱和块周围有大量"暗"可以压住它） | **不会被吸收**（底是高亮度大面积，第二块强色周围没有"暗"来压它） |
| 配额 | 1 个强色块 | **1 个强色块（不放松）** |

**为什么更严格。**

1. **深色底是"吸收性"的。** 在 L\*=3 的底上放一个高饱和块，四周的极暗会把它**框住**，第二块强色出现时，两块之间隔着一大片近黑，眼睛会自动做主次（大的赢）。深色容忍度比看上去高。
2. **浅色底是"竞争性"的。** 在 L\*=95 的底上，任何一块强色都是"白纸上的色块"，两块强色之间没有暗区做缓冲，眼睛看到的是**两个平级的焦点**。所以浅色下第二个强色块的破坏力**大于**深色。
3. **推论（新增一条纪律）**：浅色下「大面积白卡」本身**不算**强色块（它只是底的一部分），但**「白卡 + 强色」这个组合必须全页只出现一次**。也就是说，唯一强色块必须同时满足：**它是本页唯一的高饱和面，且它是本页唯一的"白底上的彩色面"**。
4. **随 §3 的语义改动，这个唯一强色块从"蓝色渐变"改判给「冰川蓝」家族**——它同时是品牌色（App 图标）和那张资产卡的卡面。这是把品牌资产和视觉焦点合并的一次刻意决策，理由见 §3 用量纪律第 3 条。

## 3 · 色语义重定义

> **本节是用户已定的决策，不是待决项。** 三个角色：**冰川蓝 = 品牌 / 图标**，**收入 = 红**，**支出 = 绿**。

### 3.1 三色双档值与对比度

**测量方法（全部数值由本次自算，非引用第三方）**：把十六进制拆成 sRGB 分量并归一化到 0–1，按 WCAG 2.x 做线性化 `c ≤ 0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4`，加权 `Y = 0.2126R + 0.7152G + 0.0722B` 得相对亮度，再用 `CR = (L_hi + 0.05) / (L_lo + 0.05)` 求对比度。L\* 走 CIE Lab 的标准式。**未使用任何第三方对比度库**（脚本自写，`pwsh` 实跑）。

#### 冰川蓝 · 品牌 / 图标（`--accent`）

| 档 | 值 | vs 页面底 | vs 卡面 | 白墨压其上 | 近黑墨压其上 |
|---|---|---|---|---|---|
| 深色档 | `#7FE3FF` | **13.43:1**（vs `#0B0B0C`） | **12.13:1**（vs `#17181A`） | **1.35:1 ✗** | **13.43:1 ✓** |
| 浅色档 | `#1B5FD0` | **5.16:1**（vs `#EFF1F4`） | **5.84:1**（vs `#FFFFFF`） | **5.84:1 ✓** | 2.71:1 ✗ |

> ⚠️ **`#F5F6F7`（白墨）压在深色档 `#7FE3FF` 上只有 1.35:1。** 这就是 §4 里冰川蓝主卡必须做特殊处理（唯一加护底、唯一不加纹理、渐变改 4 停）的根本原因——**它的亮端物理上不能承载浅色文字**。反过来说，`#0B0B0C` 压在同一个值上有 13.43:1，所以冰川蓝面上的字**必须用近黑墨**。

### 3.2 与青柠 / 铜橙的交接

v2 §1.6 的青柠 `#C8F169`（品牌点缀，面积 ≤5%）与铜橙 `#D9794F`（支出语义）**在 v3 中退役**：

| v2 角色 | v2 色值 | v3 接任者 | 交接理由 |
|---|---|---|---|
| 品牌点缀 | 青柠 `#C8F169` / 暗阶 `#8FBF3A` | **冰川蓝 `--accent`** | 用户已定「App 图标最终色：冰川蓝」。青柠与冰川蓝并列会形成**两个品牌色**，违反唯一性 |
| 支出语义 | 铜橙 `#D9794F` | **支出绿 `--expense`** | 用户已定「支出为绿色」。铜橙属暖色区，与收入红同处暖侧，**红/橙在小面积上难以区分**——这也正是把它换掉的实际收益 |
| 录音态声波 | 青柠 `#C8F169` | 冰川蓝 `--accent` | 见 1.5 第 6 条。「唯一强色块在录音时让位给录音态」的逻辑保留，只换色 |

### 3.3 用量纪律（**本节是硬约束，不是建议**）

1. **支出绿是页面主角。** 它出现在：金额数字、支出分类图标、支出折线、月度汇总条形。它是**唯一允许大面积出现的语义色**（但仍建议单块 ≤5% 面积，全页累计 ≤15%）。
2. **品牌蓝只用于图标 / 选中态 / 品牌资产。** 具体是：App 图标、底部导航当前项、分段控件的选中胶囊、那张唯一强色块资产卡的卡面。**品牌蓝不得出现在任何金额数字上。**
3. **两者不得争夺同一视觉层级。** 判据是可操作的三条：
   - 同一屏内，**品牌蓝的出现面积必须小于支出绿**（品牌是"点"，支出是"面"）；
   - 品牌蓝**不得与金额数字同处一个视觉行**（避免读成"这个数有品牌含义"）；
   - 当两者同屏时，**品牌蓝必须处在"导航/容器"位置，支出绿必须处在"内容"位置**——层级上一个是框架，一个是内容，天然不冲突。
4. **红不承担"危险"。** 收入 = 红之后，危险/删除**不得再用红**，否则用户无法判断"这个红是进账还是报错"。危险改为 **`--warn` 琥珀 + 图标形状（垃圾桶 / 感叹号）**承担。**这是本次语义重定义最容易被忽略的连带后果。**
5. **收入红与支出绿不得同时大面积为邻。** 两者对比度都够（深色 6.50 / 8.95），但**红绿色盲（约 8% 男性）下二者会趋同**。因此数字**必须同时带符号 `+` / `−`**，不允许只靠颜色区分收支——颜色是**冗余通道**，不是唯一通道。（v2 §1.3 的 `tabular-nums` 纪律与此配合：符号位必须占位对齐。）

### 4.2 文字区对比度实测（**8 张全部达标**）

**测评方法**：按 §4.0 沿用的 jessepollak 下部信息块几何，实测文字区 = `x ∈ [10%, 90%] × y ∈ [55%, 92%]`。在该矩形内按 9×7 = **63 点**均匀采样，对每一点**复合计算完整栈**（渐变底色 → 护底 scrim → 纹理 4 层叠加 → 光泽带），取**最坏一点**作为该卡的对比度。渐变按 CSS 规范的实际几何算：`linear-gradient(θ)` 方向向量 `dx = sinθ, dy = −cosθ`，线长 `L = |W·dx| + |H·dy|`，点 `P` 的 `t = 0.5 + ((P−C)·d)/L`（135deg 时 `L = 388.9`）。纹理按 alpha 逐层 `1−(1−a₁)(1−a₂)…` 累计。

| # | 卡面 | 文字墨 | 文字区最坏对比度 | 判定 |
|---|---|---|---|---|
| 1 | 冰川蓝主卡 | `#F5F6F7` | **8.11 : 1** | ✓ AA |
| 2 | 中性石墨 | `#F5F6F7` | **9.75 : 1** | ✓ AA |
| 3 | 深青 | `#F5F6F7` | **7.44 : 1** | ✓ AA |
| 4 | 冰银 | `#17181A` | **10.29 : 1** | ✓ AA |
| 5 | 暖褐 | `#F5F6F7` | **8.06 : 1** | ✓ AA |
| 6 | 午夜紫 | `#F5F6F7` | **10.08 : 1** | ✓ AA |
| 7 | 深海 | `#F5F6F7` | **10.91 : 1** | ✓ AA |
| 8 | 素瓷 | `#17181A` | **11.93 : 1** | ✓ AA |

**两条由实测得出、必须写进规范的设计原则：**

1. **「文字只放下部信息块」不是排版偏好，是对比度安全区。** 8 张卡里，下部信息块恰好落在每张渐变的**暗端**，所以**只要文字严格待在这个矩形内，就不需要护底**。一旦把文字上提到亮端，冰川蓝卡会立刻从 8.11:1 崩到 1.35:1（白墨 vs `#7FE3FF`）。
2. **护底只用一次。** 冰川蓝主卡是唯一「亮端伸进文字区」的卡，因此它是唯一需要 scrim 的（`rgba(11,11,12,.62)` @ `0%` → 透明 @ `64%`，在 `y=55%` 处 alpha ≈ 0.17）。它同时也是**唯一不加纹理层**的卡——因为叠加纹理会把已经吃紧的余量再吃掉一截。

### 4.3 光泽带缺陷（**本次最重要的一处修正**）

原配方末层光泽：`linear-gradient(-25deg, transparent 50%, rgba(255,255,255,.2) 70%, transparent 90%)`。

- 该带在 −25deg 轴上占据 `t ∈ [0.50, 0.90]`；而卡面**文字区**在同一轴上占 `t ∈ [0.089, 0.652]` → **两者重叠**。
- 实测该光泽在 `t = 0.652`（文字区最靠近它的那一角）处 alpha = **0.152**——足以把文字区背景抬亮，使冰川蓝卡的白墨从可用值掉到约 **2.9:1**。
- **修正**：光泽带改为 `linear-gradient(-25deg, transparent 70%, rgba(255,255,255,.18) 84%, transparent 98%)`。实测在 `t = 0.652` 处 alpha = **0.000**，光泽完全退到**左上角**（`t` 越大越靠左上，`t = 1.0` 是左上角、`t = 0` 是右下角）——该区域没有文字，且会顺便照亮芯片位，视觉上更合理。

> **另有一处被否决的方案**：曾考虑右上角径向光斑 `radial-gradient(circle at 84% 16%, rgba(127,227,255,.55), transparent 62%)`。其 farthest-corner 半径 = 338.6px，实测**漏进文字区的最大 alpha = 0.3424** → **否决**，光泽只走上面那条改过位置的线性带。

### 4.4 浅色页面底上的卡面边界（**新增的浅色专属问题**）

在浅色页面底 `#EFF1F4`（L\* = 95.07）上，两张浅色卡的**边缘对比度几乎为零**：

| 卡 | 亮端 vs 页面底 | 暗端 vs 页面底 |
|---|---|---|
| 冰银 | `#F2F6FA` vs `#EFF1F4` = **1.042:1** | `#C3CEDA` vs `#EFF1F4` = 1.41:1 |
| 素瓷 | `#FBF9F6` vs `#EFF1F4` = **1.077:1** | `#E3DED5` vs `#EFF1F4` = 1.18:1 |

**处理方式（与 §1.1 的禁令一致）**：冰银/素瓷在浅色底上靠 **`inset 0 1px 0 #FFFFFF` 的顶端 1px + 更柔落影** 立住，素瓷额外补一条 `0 0 0 1px rgba(23,24,26,.06)`。**不得加粗边框、不得加深渐变来硬造边界**——1.042:1 说明这两张卡在浅色下本来就是"轻"的，出路是接受它轻、靠影子托起，而不是把它画重。（深色底上不存在这个问题：石墨卡最暗端 `#17181A` vs 页面 `#0B0B0C` 有可用边界。）

### 5.6 F · 英雄照片卡（**用户已定：按卡面处理**）

v2 §11 把英雄照片卡当作"A–E 清单外的补充"，建议用图库照片。**v3 改变定性：它属于卡面层，与 §4 的 8 张默认卡面同属一族**，因此它必须遵守 §4.0 的全部几何（350×200 的 7:4、下部信息块、圆角、`--r-l` 同心关系），只是"填充"从纯渐变换成照片。

**新增的硬规则（照片卡特有）**：

1. **照片必须带护底才能承载文字。** 渐变的暗端是**已知**的（§4.2 能算出 8.11:1），照片的局部亮度是**不可知**的。所以照片卡**一律**在文字区叠一层 scrim：`linear-gradient(0deg, rgba(11,11,12,.68) 0%, rgba(11,11,12,.28) 48%, rgba(11,11,12,0) 72%)`。这一条的适用面比冰川蓝主卡更广（它是**所有**照片卡，不只是主卡）。
2. **照片的构图必须给下部信息块留位置。** 提示词里必须显式要求"画面下方 45% 区域主体不密集"。
3. **照片卡不得再叠加 §4 的纹理层。** 纹理是给纯色渐变增加"券面感"的，压在人像/风景照片上只会变脏。

## §7.5 主理人复核：三处令牌偏离 + 一个滚动条坑（2026-10-04）

原型 v2 为满足「大面积磨砂玻璃、非常透」+ WCAG，**在三处令牌上偏离了本包 §2 的取值**，都往对比度更高的方向走，语义未变：

| 令牌 | 本包 §2 | 原型实际 | 原因 |
|---|---|---|---|
| `--ink-3`（深色） | `#85878E` | `#8C8E96` | 玻璃透出环境光后最坏合成底升到 `#1E2426`，原值仅 4.39:1；提亮后 4.82:1 |
| `--ink-3`（浅色） | `#666B75` | `#5F646E` | 页面底被环境光压到 `#E4EAF2` 时仅 4.39:1；压深后 4.90:1 |
| `--expense`（浅色） | `#0F7A46` | `#0C7341` | 同口径仅 4.42:1；压深后 4.89:1 |

**口径修正（重要）**：玻璃卡一旦半透明，文字的真实背景就**不是** `--surface`，而是 `composite(玻璃, composite(环境光, 页面底))`。于是套件里按 `--surface` 算的那 16 组对比度**系统性偏乐观**（`--ink-3` 深色：按 `--surface` 是 4.95，按最坏合成只有 4.39）。验收脚本 `.proto-check/glass-contrast.js` 已改为同时算「玻璃卡上」与「页面底+环境光」两个最坏合成，12 组全 ≥4.5 才判过。**这条口径应写进后续任何玻璃化 UI 的验收。**

**一条物理上限**：玻璃要「更透」就得让背后有东西可折射（加大环境光），但**直接坐在屏幕底上的文字**（区块标题、副统计条、图表说明）会因此掉对比度 —— 环境光幅度不能只由审美决定，上限由这批文字卡住。最终取 `--amb-a/.055`、`--amb-b/.075`（深）与 `.05/.075`（浅），透明度改由玻璃自身 alpha 承担（深色玻璃 = `rgba(255,255,255,.055)` 白纱，浅色 = `rgba(255,255,255,.52)`）。

**一个真坑（Chromium）**：只要同时写了 `scrollbar-width` 或 `scrollbar-color`，**Chromium 会整体忽略 `::-webkit-scrollbar-*`** —— 这正是上一版“自定义滚动条没生效、仍带 Windows 箭头按钮”的根因。现在只保留 webkit 伪元素（轨道透明、滑块内缩 3px 成小胶囊、`::-webkit-scrollbar-button` 全部 `display:none`）；App 框内用 `scrollbar-width:none` 彻底隐藏（iOS 本来就不画）。

### 7.6 假色边：半透明面板盖在**色块**上，圆角抗锯齿会漏出一条“彩色包边”

**症状**：交易行右端沿圆角出现一条金色月牙，看着像设计里加了一圈"颜色包边"，但令牌表里没有任何暖色。

**根因**：行卡为了左滑删除，在 `.item` 上铺了一条琥珀车道（`background:var(--warn)`），上面再盖一层 `.item-face`。两层都是 `border-radius:var(--r-full)`，几何完全重合，但**各自独立做抗锯齿**：父层裁剪的边缘覆盖度与子层边缘的覆盖度在边界像素上不相等，于是父层的琥珀从这条 1px 缝隙里透出来。

**判定方法（正反证，比肉眼可靠）**：把疑似父层背景临时改成纯绿 → 那条弧线变绿；把子层背景改成品红 → 整行变品红、弧线变成两色混色。两条都成立即定死。

**修法（治本，不是调色）**：**静止态干脆不画那层色块** —— 车道改为只在已滑开时（`.item.swiped`）才画；此时子层已平移 76px、车道区域上方没有任何面板，琥珀由父层自己的圆角裁剪，边缘干净。

**通用规则（建议写进任何玻璃/半透明 UI 的规范）**：**半透明面板不要盖在异色块上** —— 抗锯齿缝隙、`backdrop-filter` 取色、以及部分平台的舍入都会让底色渗出来。要么让底块只在必要时出现，要么让面板自身不透明（本项目的滑出行卡就属于后者，见 §4 注释）。

### 7.7 伪元素描边的宿主必须自身 positioned（否则会长成一个横跨界面的巨椭圆）

**症状**：设置页「记账」分组上横着一条来历不明的细圆弧/椭圆弧，穿过了组内文字与货币档位，且深浅两模式都出现。它不属于任何设计意图。

**根因**：冰面柔光边缘是用 `::before` 画的，写法是 `inset:0; border-radius:inherit`。而 **`inset:0` 是相对「最近定位祖先」解析的**：`.pick button` 自己没有 `position`，于是伪元素没有铺满按钮，而是**铺满了它最近的定位祖先 `.group`** —— 332×290 的盒子；`border-radius:inherit` 又从胶囊按钮继承到 `999px`。**332×290 + 999px 圆角 = 一个完整的巨大椭圆**，它当然会横跨整个分组。

实测抓到的伪元素几何（`getComputedStyle(el,"::before").width/height`）：

```
::before @ BUTTON（设置页货币/配色档） host=1196,330 96×44   w=332px  h=290.094px  r=999px
::before @ BUTTON.rowcard.voice        host=60,484  332×81   w=332px  h=6719px     r=999px   ← 同一个病
```

**修法**：给**每一个**描边伪元素的宿主补上 `position:relative`（`.pick button`、`.seg button` 两个当时漏了）。`.toast` 本就是 `position:absolute`，`.card/.kpi/.group/.rowcard` 本就是 `relative`。

**为什么它难以发现（三条经验，都很通用）**：
1. **所有既有检查都看不见它**：它既不改文字对比度，也不改任何元素的盒子，只在视觉上多画一个形状；对比度套件、触摸目标套件、需求覆盖套件全部通过。
2. **`getBoundingClientRect()` 对伪元素无效**：它返回的是宿主元素的盒子——我就是因此得出了"没有任何盒子等于该椭圆"的错误结论（`document.elementsFromPoint` 也只会命中宿主，永远不会命中伪元素）。
3. **量它的几何必须靠"沿路径采样 + 亮度带计数"**：面积均值／全周均值会被界面文字淹没（实测角向命中基线 108，完全无判别力）；改用「沿椭圆每 0.5° 采一点、统计亮度落在 [45,140] 的点数」后，基线 48 → 去掉伪元素背景图 9，判别力立刻出现。工具留在 `.proto-check/hairscore.py`。
   副作用提醒：该度量对**内容变化**敏感（示例数据里"今天几号"会改变文字位置），所以它只适合同一次渲染批次的**相对比较**，不适合当回归断言。

**回归防护（已加）**：`.proto-check/static-audit-v2.js` 第 15 节会解析 `--rim-edge` 那条规则的选择器列表，逐个回查宿主的基规则是否声明了 `position`。反向验证：临时删掉 `.seg button` 的 `position:relative` → 立刻 `WARN 未定位：.seg button`。**这类"看不见的渲染缺陷"必须有一个结构性断言钉住，否则下次改样式会再长出来。**

## §7.8 主理人加 · 七条界面修正与四条通用规则（2026-10-04，用户指正后）

### 7.8.1 顶部不再放「灵动岛」黑块（用户要求"背景铺满，取消黑色的元素"）
`.dynamic-island`（112×30 纯黑圆角块）**直接从 DOM 删除**，不再用"透明度 0"这种半吊子做法。随之把 `.statusbar` 的避让改成纯 `padding`，不再依赖那一块黑来视觉占位。
**注意**：删掉它以后，顶部只剩环境光渐变——**这正是"整体感更强"的来源**：顶部不再有一个"实心异物"，屏内背景一路铺满到圆角边缘。

### 7.8.2 状态栏基线对齐（根因：图标与文字用了两套垂直定位）
- 旧法：图标（信号/Wi-Fi/电池）用 `vCenter(5)` 即 `top:5px + translateY(-50%)` 定位**中线**，而 `9:41` 与 `5G` 靠 `align-items:center` 在整行里居中 → 两类元素的"中心"不是同一个东西，实测文字比图标低约 2px。
- 修法：文字也改成**中线定位**，`.statusbar` 用 5 行横排结构（左侧文字 / 信号 / 文字 / 电池 / 右侧文字），全部 `position:absolute` + `translateY(-50%)`。
- 实测：`9:41` 墨迹底行 = 134，`5G` 墨迹底行 = 134 → **完全相等**。

### 7.8.3 标题行与右上角小字基线对齐（用户："左上角的文本方框要和右上角的方框文本对齐"）
`.nav` 由 `align-items:center` 改为 `align-items:flex-end` + 给 `.sub` 一行排版盒（`line-height:1`），使 h2 与右上小字**共用同一条基线**。
实测：`记一笔` 墨迹底行 208 vs `10 月 · 10 笔` 206（差 2px 来自 26px 与 12.5px 两档字号的 hinting，不是基线错位）。**判据要看基线，不要看"看起来在一条线上"**。

### 7.8.4 「取消 / 保存」改胶囊 + 冰面柔光边缘 + 弥散投影
`.btn{position:relative;border-radius:var(--r-full);box-shadow:var(--sh-glass)}`，并把 `.btn::before` 并入 `--rim-edge` 那条描边规则。
**这一步必须和 §7.7 一起做**：`.btn` 自己加了 `position:relative`，否则它同样会去对齐最近的定位祖先（`.sheet`）。

### 7.8.5 分类胶囊文字不居中（根因：绝对定位元素留下的 `gap` 幽灵位）
症状：手动记账弹层里「分类」的胶囊，文字肉眼可见偏右。
根因：色点 `<span class="sw">` 被改成 `position:absolute` 后**脱离了 flex 流**，但容器的 `gap:6px` 仍然按"两个子项"计入一份间距 → 文本整体右移约 6px；又因为色点让左侧显得更空，读起来像"没居中"。
修法：`.chipsel{gap:0;justify-content:center}`，色点 `position:absolute;left:11px`。
**通用规则（新增）**：**给 flex 容器塞绝对定位子元素之前，先把它的 `gap` 清掉** —— 否则会留下一个任何检查都测不到的"幽灵间距"。

### 7.8.6 删除车道从琥珀改冰川蓝（用户指定）——以及它的代价
`.item.swiped{background:var(--accent)}`、`.item-del{color:var(--accent-ink)}`。
**必须如实写进规范的代价**：琥珀原本是"危险"语义的唯一承载体；换成品牌冰川蓝后，**颜色不再表达危险**。因此「垃圾桶图标 + 删除文字」这两条通道从"冗余"升级为**承重项**——不能只留其中一个。`smoke-v2.js` 的对应断言因此**加严**（必须同时存在垃圾桶 `svg` 与"删除"二字），而不是放宽。
遗留：冻结的 v1 契约套件（`smoke.js`）里那条断言原文写的是"用琥珀色"，本次未改 v1 契约；v2 套件已按新语义重命名迁移。

### 7.8.7 统计页「历史查询」二级菜单（用户新增的功能，不是纯视觉）
- 新增帧状态 `anchor`（`{y,m}` 历史锚点，`null` = 看现在）与 `jump`（菜单草稿）。
- `rangeBounds(range, anchor)` 语义升级：**`end` 统一 clamp 到今天**；锚在过去时，月/季/年各自按**自然月末 / 季末 / 年末**收口，不会被截断在"今天"。
- 入口：右上角月份按钮（`.jump`，带 caret，`aria-haspopup="dialog"`）；面板：月 / 年份两列 + 现在 / 完成（`现在` = 清空锚点）。面板复用 `.card` 的玻璃与描边（`position:absolute`，故 §7.7 问题不存在）。

### 7.8.8 浅色模式语音胶囊的「黑边」（用户："浅色模型下语音胶囊按钮周围会有一圈单独的黑色边框"）
根因：`--rim-edge` 在浅色模式走**白色**渐变，而语音行在两种模式下都是**近黑填充**；白色描边压在近黑底上，读出来就是"一圈灰黑的独立边框"。深色模式看不出来，是因为深色的描边底色本来就接近页面底。
修法：`[data-palette="light"] .rowcard.voice::before{display:none}`，这一行改由弥散投影与页面分层。
实测：跨胶囊边缘横扫，页面 (238,240,243) → 约 10px 的柔和过渡（236→234）→ 胶囊 (23,24,26)，**没有任何独立暗线**。
**通用规则（新增）**：**描边色不能只按"页面底"选** —— 近黑或高饱和填充的控件要单独给描边色，或干脆不描边。

### 7.8.10 屏内不能有「上下两块」：整屏材质必须挂在屏幕级容器上（**用户第二轮指正**）
**症状**：用户圈出标题下方那块区域——「可以非常明显地看见不同的分层」。标题以上是一片纯底，往下突然换成带光斑的底，交界处还能看见光斑被裁切的圆弧。

**根因**：屏内环境光（三条 `radial-gradient`）挂在 `.scroll` 上，而 `.scroll` 是**从标题下方才开始**的。于是"屏幕底"实际由两块不同材质拼成：`.screen` 的纯 `--bg` + `.scroll` 的径向光斑。

**修法**：环境光上移到 `.screen`（整屏一张连续底；`.screen` 本就有 `overflow:hidden` + `border-radius:42px`，天然裁到圆角内），`.scroll` 的背景属性整段留空。副作用是环境光**不再跟着内容滚动**——这本就是"屏内光照"应有的行为。

**为什么四套检查全绿也漏掉**：它不改令牌、不改盒子、不改任何对比度，只是把"底"画成了两块。→ 已加结构断言（`static-audit-v2` 第 16 节）：`radial-gradient` **必须在 `.screen` 规则里、且不得出现在 `.scroll` 规则里**。

**通用规则（新增，适用于任何一屏式 UI）**：**「页面底」只能有一个来源。** 任何整屏材质——背景、环境光、噪点、扫描线——都必须挂在**屏幕级容器**上；一旦挂在滚动容器上，就必然在滚动区起点形成一道横向分层。同一类缺陷还包括：给 `.scroll` 单独画 `background`、给状态栏/导航条单独画不透明底。判据是"把整屏缩小到 10% 看，底是不是一整片"。

### 7.8.11 顶部右侧小字统一成胶囊（用户：「这些文本元素都做成和‘统计’左上角的胶囊元素」）
用户写的"统计左上角"，实际指的是**统计页右上角那个月份入口**（页面里唯一一个胶囊状元素）——按其意图按"同一种胶囊语言"处理：`.nav .sub` 现在与 `.nav .jump` 完全同源——
`border:1px solid var(--line-control)` + `background:var(--surface-2)` + `border-radius:var(--r-full)` + `padding:5px 12px` + `min-height:30px`。
四个屏的右上角（`10 月 · 10 笔` / 月份入口 / `10 笔 · ¥3,144.50`）因此读起来是同一族控件，而不是三种不同的裸文字。
断言：两条规则都必须带 `border-radius:var(--r-full)`（同第 16 节）。
